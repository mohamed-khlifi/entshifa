--------------------------------------------------------------------------------
1. THE TEN RULES THIS ARCHITECTURE ENFORCES
--------------------------------------------------------------------------------

 R1. Dependencies point inward. Routers depend on services, services depend on
     repositories and domain logic. Nothing in the domain layer imports FastAPI,
     SQLAlchemy or HTTP.

 R2. One feature owns one domain. Code is grouped by clinical domain (patients,
     audiology, endoscopy), never by technical type. There is no global
     "models" folder holding 80 unrelated tables.

 R3. Only repositories touch the database. Services never write a query.
     Routers never see an ORM object.

 R4. Clinical math is a pure function. Every calculation takes plain inputs and
     returns a plain result. No DB, no HTTP, no globals. That is what makes it
     testable against published reference values.

 R5. Everything crossing a boundary is a typed schema. Pydantic on the backend,
     TypeScript types generated from the OpenAPI spec on the frontend. No dicts
     with magic keys.

 R6. No user-visible string is hardcoded. Not in the UI, not in reports, not in
     error messages. Strings are keys; clinical terms are database rows.

 R7. Reference data is data, not code. Drug formulary, questionnaires, protocols,
     procedure catalog, allergen panels live in versioned tables an admin can
     edit.

 R8. Clinical records are append-only once signed. Corrections are addenda.
     Every read and write is audited.

 R9. Every clinical value carries its provenance: who recorded it, when, from
     which device or person, and whether a human confirmed it.

 R10. If it happens more than twice, it becomes a reusable primitive. Base
     repository, base service, form factory, query factory, map component.
     Write it once, use it in fifteen places.


--------------------------------------------------------------------------------
2. LAYERING MODEL AND THE DEPENDENCY DIRECTION
--------------------------------------------------------------------------------

  HTTP request
      |
      v
  +-------------------------------------------------------------+
  |  API layer         router.py, dependencies.py                |
  |  - parse and validate input (Pydantic)                       |
  |  - resolve current user, clinic, permissions                 |
  |  - call ONE service method                                   |
  |  - map domain errors to HTTP responses                       |
  |  - never contains business rules, never touches the DB       |
  +-------------------------------------------------------------+
      |
      v
  +-------------------------------------------------------------+
  |  Service layer     service.py                                |
  |  - orchestrates a use case end to end                        |
  |  - enforces business rules and invariants                    |
  |  - owns the transaction boundary (unit of work)              |
  |  - calls repositories, engines, other services, event bus    |
  |  - never builds SQL, never returns ORM objects outward       |
  +-------------------------------------------------------------+
      |                          |                        |
      v                          v                        v
  +------------------+  +---------------------+  +-------------------+
  | Repository layer |  | Domain layer        |  | Integration layer |
  | repository.py    |  | calculations.py     |  | storage, email,   |
  | - all queries    |  | rules.py            |  | SMS, PDF, AI      |
  | - no business    |  | policies.py         |  | - adapters behind |
  |   rules          |  | value objects       |  |   interfaces      |
  +------------------+  | PURE FUNCTIONS ONLY |  +-------------------+
      |                 +---------------------+
      v
  +-------------------------------------------------------------+
  |  Persistence       models.py (SQLAlchemy), MySQL             |
  +-------------------------------------------------------------+

  Allowed imports (enforced by an import-linter rule in CI):

    router      -> service, schemas, dependencies, core
    service     -> repository, domain, schemas, integrations, core, events
    repository  -> models, core
    domain      -> nothing but stdlib, typing and core.types
    models      -> core.db only

  Forbidden, and CI fails on them:

    router      -> repository        (skipping the service layer)
    router      -> models            (leaking ORM to HTTP)
    repository  -> service           (circular)
    domain      -> models, fastapi, sqlalchemy, requests

3. REPOSITORY LAYOUT (MONOREPO)
--------------------------------------------------------------------------------

One repository, three deployable pieces, shared contracts. This keeps the API
types and the frontend types from drifting apart.

ent-workspace/
├── apps/
│   ├── api/                      FastAPI application
│   ├── web/                      Next.js application
│   └── worker/                   background jobs (shares api code)
│
├── packages/
│   ├── contracts/                generated OpenAPI spec + generated TS types
│   ├── i18n-messages/            all UI translation catalogs (shared)
│   └── config/                   shared eslint, tsconfig, prettier presets
│
├── infra/
│   ├── docker/                   Dockerfiles, docker-compose for local dev
│   ├── migrations/               (optional) SQL snapshots for DBAs
│   ├── nginx/                    reverse proxy config
│   └── scripts/                  backup, restore, seed, anonymize
│
├── docs/
│   ├── architecture/             ADRs (architecture decision records)
│   ├── clinical/                 the feature spec, score references, sources
│   └── runbooks/                 deploy, incident, restore procedures
│
├── .github/workflows/            CI pipelines
├── Makefile                      one-word commands: make dev, make test, make seed
└── README.md

Why a monorepo: the OpenAPI schema is generated from FastAPI, TypeScript types
are generated from that schema, and the frontend imports them. One command
(`make contracts`) regenerates both. A backend field rename becomes a frontend
compile error instead of a runtime bug in a clinic.

5. ANATOMY OF A FEATURE MODULE
--------------------------------------------------------------------------------

Every feature folder has the same shape. A developer who has seen one has seen
them all. Files that a feature does not need simply do not exist.

features/audiology/
├── __init__.py
├── router.py             HTTP endpoints. Thin. One service call each.
├── dependencies.py       feature-specific FastAPI dependencies
├── schemas/
│   ├── requests.py       AudiogramCreate, ThresholdInput, TympanogramCreate
│   ├── responses.py      AudiogramRead, AudiologyDashboard, ComparisonRead
│   └── internal.py       DTOs passed between service and engines
├── models.py             SQLAlchemy models owned by this feature
├── repository.py         AudiogramRepository, TympanometryRepository
├── service.py            AudiologyService: use cases
├── selectors.py          read-optimized queries for dashboards/lists
├── policies.py           "can this user see this audiogram" rules
├── events.py             AudiogramCreated, BaselineChanged
├── handlers.py           reacts to events from other features
├── constants.py          FREQUENCIES_HZ, SYMBOLS, DEFAULT_PTA_FORMULA
├── exceptions.py         AudiogramNotFound, IncompleteThresholds
└── tests/
    ├── test_service.py
    ├── test_repository.py
    └── test_router.py

Where each kind of logic goes, with concrete examples:

  "Compute the PTA"                      -> engines/audiology/pta.py (pure)
  "Load the last 5 audiograms"           -> repository.py
  "Create an audiogram, compute metrics,
   flag asymmetry, emit an event"        -> service.py
  "POST /audiograms returns 201"         -> router.py
  "Only the owning clinic may read it"   -> policies.py
  "When an audiogram is created, cancel
   the pending 'audiogram due' recall"   -> handlers.py (listens to the event)
  "Dashboard query joining 6 tables"     -> selectors.py

Rule of thumb for file size: if router.py exceeds ~200 lines, split it by
sub-resource (audiograms.py, tympanometry.py, devices.py) inside a routes/
folder. If service.py exceeds ~400 lines, split by use case group.

6. THE CORE PACKAGE (WHAT EVERY FEATURE REUSES)
--------------------------------------------------------------------------------

core/ is written once, early, and then barely changes. It is what makes adding
the fifteenth feature take a day instead of a week. Contents:

  db/mixins.py        PublicIdMixin (ULID), TimestampMixin (created_at,
                      updated_at), AuditMixin (created_by_id, updated_by_id),
                      SoftDeleteMixin (deleted_at, deleted_by_id),
                      TenantMixin (clinic_id + automatic query filter),
                      VersionMixin (optimistic locking with a version column)

  db/types.py         ULIDType (CHAR(26), sortable), EncryptedString
                      (application-level AES-GCM for the few fields that need
                      it), LocalizedText (JSON keyed by locale), Laterality
                      enum, Quantity composite (value + unit)

  db/unit_of_work.py  async context manager that opens a transaction, commits
                      on success, rolls back on any exception, and flushes
                      collected domain events after commit

  repository/base.py  generic CRUD + filtering + pagination (section 7.1)

  schemas/base.py     CamelModel: Pydantic base that serializes snake_case
                      Python to camelCase JSON automatically, so the backend
                      stays pythonic and the frontend stays idiomatic

  schemas/common.py   the clinical value objects reused everywhere:
                      CodeableConcept {conceptId, code, system, display}
                      Quantity {value, unit, system}
                      Laterality {right | left | bilateral | midline | na}
                      Period {start, end}
                      Attachment {id, url, contentType, title}
                      Provenance {recordedBy, recordedAt, source, confirmed}

  errors/             one exception hierarchy, one HTTP mapping, one error
                      code per failure mode so the frontend can translate it

  security/           authentication, permission checks, tenant resolution

  i18n/               locale negotiation and server-side translation

  events/             in-process pub/sub so features stay decoupled

  audit/              request context and audit writing

7.1 Generic repository
--------------------------------------------------------------------------------

# core/repository/base.py
from typing import Generic, TypeVar, Sequence, Any
from sqlalchemy import select, func, update
from sqlalchemy.ext.asyncio import AsyncSession

ModelT = TypeVar("ModelT")

class BaseRepository(Generic[ModelT]):
    model: type[ModelT]

    def __init__(self, session: AsyncSession, clinic_id: int | None = None):
        self.session = session
        self.clinic_id = clinic_id          # tenant scope, applied automatically

    def _base_query(self):
        stmt = select(self.model)
        if hasattr(self.model, "deleted_at"):
            stmt = stmt.where(self.model.deleted_at.is_(None))
        if self.clinic_id and hasattr(self.model, "clinic_id"):
            stmt = stmt.where(self.model.clinic_id == self.clinic_id)
        return stmt

    async def get(self, id_: int) -> ModelT | None:
        return await self.session.scalar(
            self._base_query().where(self.model.id == id_)
        )

    async def get_by_public_id(self, public_id: str) -> ModelT | None:
        return await self.session.scalar(
            self._base_query().where(self.model.public_id == public_id)
        )

    async def list(self, *, filters=None, sort=None, page=None) -> Page[ModelT]:
        stmt = apply_filters(self._base_query(), self.model, filters)
        total = await self.session.scalar(
            select(func.count()).select_from(stmt.subquery())
        )
        stmt = apply_sort(stmt, self.model, sort)
        stmt = apply_pagination(stmt, page)
        rows = (await self.session.scalars(stmt)).all()
        return Page(items=rows, total=total, page=page)

    async def add(self, entity: ModelT) -> ModelT:
        self.session.add(entity)
        await self.session.flush()
        return entity

    async def soft_delete(self, id_: int, by_user_id: int) -> None:
        await self.session.execute(
            update(self.model)
            .where(self.model.id == id_)
            .values(deleted_at=func.now(), deleted_by_id=by_user_id)
        )

7.2 Unit of work and transactional services
--------------------------------------------------------------------------------

# core/db/unit_of_work.py
class UnitOfWork:
    def __init__(self, session_factory, event_bus):
        self._session_factory = session_factory
        self._bus = event_bus
        self.events: list[DomainEvent] = []

    async def __aenter__(self):
        self.session = self._session_factory()
        await self.session.begin()
        return self

    async def __aexit__(self, exc_type, *_):
        if exc_type:
            await self.session.rollback()
        else:
            await self.session.commit()
            for event in self.events:        # published only after commit
                await self._bus.publish(event)
        await self.session.close()

    def emit(self, event: DomainEvent) -> None:
        self.events.append(event)

Services use it so that a failed PDF render never leaves a half-created record:

class AudiologyService(BaseService):
    async def create_audiogram(self, data: AudiogramCreate, user: CurrentUser):
        async with self.uow as uow:
            patient = await self.patients.get_or_raise(data.patient_id)
            audiogram = Audiogram.from_input(data, recorded_by=user.id)
            metrics = compute_audiogram_metrics(          # pure engine call
                thresholds=data.thresholds,
                pta_formula=self.settings.pta_formula,
            )
            audiogram.apply_metrics(metrics)
            baseline = await self.repo.get_baseline(patient.id)
            if baseline:
                audiogram.shift = evaluate_threshold_shift(baseline, audiogram)
            await self.repo.add(audiogram)
            uow.emit(AudiogramCreated(audiogram.id, patient.id))
            return AudiogramRead.model_validate(audiogram)

7.3 Declarative filtering and pagination
--------------------------------------------------------------------------------

One filter mechanism for every list endpoint, so the frontend learns it once:

class PatientFilter(FilterSet):
    search:        str  | None = SearchOn("last_name", "first_name", "mrn",
                                          "phone", normalize=True)
    sex:           Sex  | None = Eq("sex")

Cursor pagination for timelines and long lists (stable under inserts), offset
pagination for admin tables. Both return the same envelope:

7.4 Domain errors with translatable codes
--------------------------------------------------------------------------------

# core/errors/exceptions.py
class DomainError(Exception):
    code: str = "domain_error"
    http_status: int = 400
    def __init__(self, message: str = "", **context):
        self.context = context
        super().__init__(message or self.code)

class NotFoundError(DomainError):      code, http_status = "not_found", 404
class PermissionDeniedError(DomainError): code, http_status = "forbidden", 403
class ConflictError(DomainError):      code, http_status = "conflict", 409
class ValidationError(DomainError):    code, http_status = "validation_failed", 422
class ClinicalSafetyError(DomainError):code, http_status = "safety_block", 409
class RecordLockedError(DomainError):  code, http_status = "record_signed", 409

Handlers convert these to RFC 7807 problem documents:

  {
    "type": "https://errors.entapp.io/safety_block",
    "title": "Prescription blocked",
    "status": 409,
    "code": "prescription.allergy_conflict",
    "detail": null,
    "context": { "drugName": "Amoxicillin", "allergen": "penicillin" },
    "requestId": "01J8Z..."
  }

The `code` plus `context` is what the frontend translates. The backend never
sends an English sentence that the UI has to display verbatim.

7.5 Domain events
--------------------------------------------------------------------------------

Events keep features from importing each other. Endoscopy does not need to know
that the recall engine exists.

  EncounterSigned          -> documents: render final PDFs
                           -> recalls: materialize plan items
                           -> analytics: refresh counters
  ProcedurePerformed       -> recalls: apply protocol (pack removal, tube check)
  AudiogramCreated         -> recalls: close "audiogram due"
                           -> alerts: re-evaluate only-hearing-ear flag
  SurgeryCompleted         -> questionnaires: schedule 3/6/12-month outcomes
                           -> recalls: post-op pathway
  QuestionnaireCompleted   -> encounters: attach score to the visit
  SpecimenSent             -> recalls: result review in 7-10 days

# core/events/bus.py
class EventBus:
    def __init__(self): self._handlers = defaultdict(list)
    def subscribe(self, event_type, handler): self._handlers[event_type].append(handler)
    async def publish(self, event):
        for handler in self._handlers[type(event)]:
            await enqueue_or_call(handler, event)   # async ones go to the worker

--------------------------------------------------------------------------------
8. CLINICAL ENGINES (THE PART THAT MUST NEVER BE WRONG)
--------------------------------------------------------------------------------

Everything in engines/ obeys four rules:

  1. Pure functions. Inputs in, result out. No session, no clock, no config
     lookup. If it needs "now", it is passed in.
  2. Explicit versioning. Each engine module exposes VERSION and REFERENCE.
     Results are stored with the version that produced them.
  3. Typed results, not tuples. A calculation returns a dataclass with the
     value, the unit, the inputs used, the formula name, any flags raised and
     the reference citation.
  4. Known-answer tests. Every engine has a test file with cases taken from
     the original publication or a worked example, with the source cited in
     the test docstring.

Example shape:

@dataclass(frozen=True)
class CalculationResult:
    code: str                 # "audiology.pta"
    value: float | int | str
    unit: str | None
    inputs: dict
    formula: str              # "PTA4 = mean(500, 1000, 2000, 4000)"
    version: str              # "1.2.0"
    reference: str            # "WHO 2021 grades of hearing impairment"
    flags: list[Flag]         # e.g. Flag("asymmetry_criterion_met", ...)

VERSION = "1.2.0"

def pure_tone_average(thresholds: dict[int, float], formula: PtaFormula) -> CalculationResult:
    ...

The calculator registry exposes them uniformly so one endpoint serves all of
them and the frontend can render any calculator from its metadata:

  GET  /api/v1/calculators                 -> list with inputs + units + refs
  GET  /api/v1/calculators/audiology.pta   -> input schema, formula, reference
  POST /api/v1/calculators/audiology.pta   -> CalculationResult

The narrative renderer is also an engine: structured findings in, localized
sentences out, with grammar rules per language (French adjective agreement and
gender, Arabic RTL and dual forms, English plain). This is why reports can be
produced in a language different from the one used during data entry.


--------------------------------------------------------------------------------
9. BACKGROUND JOBS AND SCHEDULING
--------------------------------------------------------------------------------

The worker shares the same codebase and imports the same services. Job rules:

  - Every task is idempotent and takes an idempotency key, so a retry cannot
    send the same SMS twice or render two PDFs.
  - Every task takes IDs, never ORM objects or full payloads.
  - Retries with exponential backoff; a dead-letter table for permanent
    failures, visible in the admin panel.
  - Long user-facing jobs (PDF batch, export) write progress to a jobs table
    the frontend polls.

Scheduled jobs:
  every 5 min   dispatch queued notifications
  hourly        recompute recall due status, escalate overdue
  daily 02:00   send questionnaire links due today (post-op outcomes)
  daily 03:00   media cleanup, thumbnail backfill, orphan file sweep
  daily 04:00   database backup verification hook
  weekly        analytics rollups, retention policy pass
  monthly       reference-data update check (formulary, protocol versions)


--------------------------------------------------------------------------------
10. BACKEND TESTING LAYOUT
--------------------------------------------------------------------------------

  tests/unit/           engines and pure logic. Milliseconds. No database.
                        Target: 100% of engines/ covered.
  tests/clinical/       known-answer tests per score and formula, each citing
                        its source. These are the tests that let a doctor trust
                        the software.
  tests/integration/    repositories and services against a real MySQL in
                        Docker, wrapped in a rolled-back transaction per test.
  tests/api/            endpoint contract tests: status codes, permissions,
                        tenant isolation, error codes, pagination envelope.
  tests/factories/      factory-boy factories per model so a test needing a
                        patient with three audiograms writes one line.

Non-negotiable test cases that must exist from the start:
  - a user from clinic A cannot read any record of clinic B (run for every
    resource, generated by a parametrized test over the router table)
  - a signed encounter cannot be mutated
  - a prescription for a known allergen is blocked
  - every calculator returns its documented value for its reference case
  - every list endpoint enforces pagination limits

13.1 API client

// lib/api/client.ts
export async function apiFetch<T>(path: string, init: RequestInit & {
  locale?: string; clinicId?: string;
} = {}): Promise<T> {
  const res = await fetch(`${API_URL}${path}`, {
    ...init,
    headers: {
      "Content-Type": "application/json",
      "Accept-Language": init.locale ?? getLocale(),
      "X-Clinic-Id": init.clinicId ?? getActiveClinicId(),
      "X-Request-Id": crypto.randomUUID(),
      ...init.headers,
    },
    credentials: "include",
  });
  if (!res.ok) throw await toAppError(res);   // problem+json -> typed error
  return res.status === 204 ? (undefined as T) : res.json();
}

Every error thrown carries `code` and `context`, and the UI renders
`t(`errors.${error.code}`, error.context)`. No English strings from the server
reach the screen.

13.4 Autosave
--------------------------------------------------------------------------------

Consultations must survive a crashed tablet.

  - Debounced (2 s idle, or 15 s maximum) PATCH of the dirty subset only.
  - Draft snapshot mirrored to IndexedDB with an encounter id, so a reload
    restores unsaved values before the network answers.
  - Optimistic concurrency: every PATCH sends the record `version`; a 409
    opens a conflict panel showing both versions rather than overwriting.
  - A visible state machine in the status bar: idle / saving / saved / offline
    / conflict, never a silent failure.

13.5 DataTable
--------------------------------------------------------------------------------

One table component (TanStack Table + shadcn) used by every list: patients,
recalls, waiting list, documents, admin tables. It handles column definitions,
server-side sorting and pagination, URL-synced filters, column visibility,
density, row selection, bulk actions, sticky header, empty and error states,
loading skeletons and CSV export. Adding a new list is defining columns.

13.6 Permission gate
--------------------------------------------------------------------------------

  <Can permission="encounter.sign" fallback={null}>
    <Button onClick={sign}>{t("encounter.sign")}</Button>
  </Can>

and `usePermission("prescription.create")` for logic. The server re-checks
everything; the client gate only avoids showing impossible actions.

13.7 Test automation hooks (`data-testid`)
--------------------------------------------------------------------------------

The product ships in multiple locales and RTL. Automated tests must not break
when copy changes or when the suite runs in French or Arabic. Every interactive
control and every element tests assert on carries a stable `data-testid`
assigned in one place.

Location (only):
  apps/web/src/lib/test/test-id.ts     factory + static registry + dynamic helpers
  apps/web/e2e/                        Playwright helpers that wrap getByTestId

Factory shape:

  testId("auth", "login", "email")           -> "auth.login.email"
  testIdProps(testIds.auth.login.email)      -> { "data-testid": "auth.login.email" }
  patientRowTestId(publicId)                 -> "patients.list.row.<publicId>"

Rules:
  - Dot-separated, lower camel segments mirroring feature area (same discipline
    as query keys and translation namespaces). No spaces, no translated words.
  - Static screens: entries in a `testIds` const tree. Dynamic rows/cells: typed
    helper functions; public ULIDs in the last segment when targeting one record.
  - Never concatenate test id strings in JSX. Never use visible text, placeholders,
    or getByRole name as the primary E2E selector.
  - Shared components own the attribute: TextField applies test id from `name`,
    DataTable from column id, PageHeader from `titleKey` or explicit `testId`
    prop. Feature pages pass semantic names, not raw strings.
  - Coverage: buttons, links, inputs, dialogs, toasts, tabs, nav items, list
    rows, empty/error/loading states, and layout landmarks (shell, sidebar, main).

Playwright:
  page.getByTestId(testIds.auth.login.submit).click()
  The same step definition runs in en, fr, and ar without change.

CI (with P0-14): eslint discourages inline data-testid literals outside the
factory; optional check that new interactive components in shared folders export
a test id contract.

16. STATE, CACHING AND DATA-FETCHING RULES
--------------------------------------------------------------------------------

  - Server state lives in TanStack Query. Never copy it into useState.
  - Client state (open panels, selected side, active tab) lives in local
    component state or a small Zustand store per feature when it must be
    shared. There is no global Redux-style store.
  - URL state (filters, pagination, selected patient tab) lives in the URL so
    a doctor can bookmark and share a view, and a refresh keeps the context.
  - Server Components fetch read-only data for first paint (patient header,
    timeline first page). Anything interactive is a Client Component.
  - Mutations always: optimistic update where safe, invalidate the precise
    query keys, roll back on error, toast with a translated message.
  - staleTime defaults: reference data 1 hour, patient record 30 seconds,
    dashboards 60 seconds, terminology 24 hours (it barely changes).
  - Prefetch on hover for patient rows and timeline events, so opening a chart
    feels instant in a busy clinic.

--------------------------------------------------------------------------------
18. FOUR KINDS OF TEXT, FOUR DIFFERENT MECHANISMS
--------------------------------------------------------------------------------

This is the part most projects get wrong by treating all text the same. There
are four distinct categories and each needs its own mechanism.

  A. UI chrome            buttons, labels, menus, validation messages.
                          -> translation files in the repo, keyed strings.
                          Changes with releases. Developers own it.

  B. Clinical terminology findings, diagnoses, procedures, anatomy, drug names,
                          questionnaire items.
                          -> DATABASE ROWS with per-locale translations.
                          Changes without a deploy. Clinicians own it.

  C. Generated narrative  the sentences in reports built from findings.
                          -> narrative engine with per-language grammar rules
                          and phrase templates stored as data.

  D. User-authored text   the doctor's own conclusion, clinic footer, custom
                          handouts, personal phrase library.
                          -> stored as written, tagged with its language.
                          Never machine-translated silently.

Mixing these up is what produces a French UI with English findings, or a
report that cannot be produced in Arabic because the sentences were hardcoded.

--------------------------------------------------------------------------------
19. UI TRANSLATION, FORMATTING, RTL
--------------------------------------------------------------------------------

  - Library: next-intl (or an equivalent with server-component support).
  - Routing: locale as the first URL segment (/fr/patients/123). Middleware
    negotiates from the URL, then the user's saved preference, then the
    Accept-Language header, then the clinic default.
  - Catalogs: one JSON file per feature per locale, so merge conflicts stay
    small. Keys are namespaced and semantic, never the English text itself:
        "audiology.audiogram.actions.addThreshold"    good
        "Add threshold"                                bad
  - ICU message format for plurals, gender and interpolation:
        "recalls.overdue": "{count, plural, =0 {No recalls} one {# recall} other {# recalls}} overdue"
    French and Arabic plural rules differ from English; ICU handles it. Arabic
    has six plural categories, which is exactly why ad-hoc string concatenation
    must be banned.
  - Formatting always through lib/i18n/format.ts: dates, times, numbers,
    decimal separators (French uses a comma), units, and name order. Never
    `date.toLocaleDateString()` inline.
  - Medical units are NOT translated: dB HL, Hz, daPa, mL, mg/kg, mmHg stay as
    they are in every language. Only the surrounding words translate.
  - RTL: `dir` is set on <html> from the locale. Layout uses logical CSS
    properties (margin-inline-start, padding-inline-end, inset-inline) so
    nothing needs a mirrored stylesheet. Icons that imply direction (back,
    next, chevrons) flip through a small utility; icons that do not (an ear, a
    nose) never flip. Charts, audiograms and anatomical maps do NOT mirror:
    clinical conventions are direction-independent, and a mirrored audiogram
    would be dangerous.
  - Fonts: a Latin family and an Arabic family loaded per locale, with
    matching x-height so the UI does not jump between languages.
  - Missing keys fail the build in CI, and fall back to the default locale at
    runtime with a logged warning, never showing a raw key to a doctor.

--------------------------------------------------------------------------------
20. CLINICAL TERMINOLOGY AS TRANSLATED DATA
--------------------------------------------------------------------------------

Every clinical term the user sees or picks is a row in `concept`, with its
display names in `concept_translation`. That single decision gives you:

  - a French UI that can print an Arabic patient handout and an English
    referral letter from the same stored data,
  - adding a language without touching application code,
  - a clinic that can rename a term locally without a deploy,
  - findings that stay comparable across languages because the stored value is
    a concept id, not a word.

Resolution order when displaying a concept: clinic override in the requested
locale -> global translation in the requested locale -> translation in the
clinic's default locale -> concept code with a "missing translation" marker
that admins can see in a dedicated screen.

The frontend caches the concept dictionary per locale (it is large but static),
loads it once per session, and resolves ids to labels locally, so a list of 200
findings does not need 200 lookups.

--------------------------------------------------------------------------------
21. DOCUMENT AND TEMPLATE TRANSLATION
--------------------------------------------------------------------------------

  - Each patient has a `preferred_document_locale`. The referring doctor may
    have a different one. A single visit can therefore produce: a chart report
    in the clinic locale, a patient handout in Arabic, and a referral letter in
    French. All from the same structured data.
  - Templates are versioned rows with a body per locale, edited in an admin
    screen with a preview. Placeholders are typed and validated
    ({{patient.fullName}}, {{audiogram.ptaRight}} with unit), so a template
    cannot reference a field that does not exist.
  - The narrative engine holds phrase templates per concept per locale:
        concept: tm.perforation.central
        en: "central perforation of the {{quadrants}} quadrant(s)"
        fr: "perforation centrale du/des quadrant(s) {{quadrants}}"
        ar: "..."
    plus per-language ordering and agreement rules (French adjective gender
    and number, Arabic dual forms, English simple plurals).
  - PDF rendering must support RTL, Arabic shaping and bidirectional text.
    Verify the renderer with a real Arabic report early, not at the end. Table
    column order also flips in RTL documents while numeric columns keep their
    alignment.

--------------------------------------------------------------------------------
22. RULES THAT KEEP LANGUAGES FROM ROTTING
--------------------------------------------------------------------------------

  1. No string literal in JSX or in a Python response. An eslint rule and a
     ruff check enforce it.
  2. Adding a key without adding it to every locale fails CI (a script diffs
     the catalogs).
  3. A "translation coverage" admin screen shows untranslated concepts per
     locale, sorted by usage frequency, so the clinic fixes what matters.
  4. Pseudo-locale (`en-XA`) in dev: renders every string with accents and
     40% extra length, exposing truncation and hardcoded strings immediately.
  5. Every new language is a data task plus a font, never a code task. If
     adding Spanish requires a developer, the design has failed.

--------------------------------------------------------------------------------
23. CONVENTIONS THAT APPLY TO EVERY TABLE
--------------------------------------------------------------------------------

  Engine and charset
    InnoDB, utf8mb4, collation utf8mb4_0900_ai_ci (accent- and case-insensitive
    search, correct for French accents and Arabic). Use utf8mb4_0900_as_cs on
    columns where case matters (codes, tokens).

  Keys
    id            BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY  (internal joins)
    public_id     CHAR(26) NOT NULL UNIQUE                    (ULID, used in
                  every URL and API payload; never expose sequential ids,
                  they leak patient volume and allow enumeration)

  Tenancy
    clinic_id     BIGINT UNSIGNED NOT NULL on every clinical table, always the
                  first column of the main composite index. Every query is
                  scoped by it at the repository level.

  Audit columns (on every table that a human edits)
    created_at    DATETIME(6) NOT NULL DEFAULT CURRENT_TIMESTAMP(6)
    updated_at    DATETIME(6) NOT NULL DEFAULT CURRENT_TIMESTAMP(6)
                  ON UPDATE CURRENT_TIMESTAMP(6)
    created_by_id BIGINT UNSIGNED NULL  -> users.id
    updated_by_id BIGINT UNSIGNED NULL  -> users.id
    deleted_at    DATETIME(6) NULL      (soft delete; clinical data is never
                  hard-deleted outside a legal erasure procedure)
    deleted_by_id BIGINT UNSIGNED NULL
    version       INT UNSIGNED NOT NULL DEFAULT 1   (optimistic locking)

  Naming
    tables        snake_case, singular  (patient, encounter, audiogram)
    columns       snake_case; booleans start with is_/has_ (is_active)
    dates         *_at for datetimes, *_date for dates, *_on for day-precision
    foreign keys  <referenced_table>_id
    indexes       ix_<table>__<cols>, uq_<table>__<cols>, fk_<table>__<ref>
    enums         stored as VARCHAR with a CHECK constraint, or as a lookup
                  table when clinicians may extend the list. Never MySQL ENUM
                  (altering it locks and it does not translate).

  Time and dates
    All timestamps stored UTC in DATETIME(6). Clinical dates that are
    inherently local (date of surgery, date of birth) stored as DATE. Each
    clinic has a timezone; conversion happens at the edges only.

  Money
    DECIMAL(12,3) plus a currency column. Never floats.

  Clinical numerics
    Thresholds, scores and measurements as SMALLINT/DECIMAL with explicit
    units in a sibling column or fixed by the table's contract. Never floats
    where exactness matters.

  Laterality
    VARCHAR(10) CHECK IN ('right','left','bilateral','midline','na'). A
    bilateral finding on a paired structure is stored as TWO rows, one per
    side, so comparisons and counts stay correct.

  JSON
    Allowed only for genuinely schemaless payloads (device raw export, AI
    request metadata, template placeholders map). Never for anything you will
    filter, sort or aggregate on. If you want to query it, it is a column.

  Deletion policy
    ON DELETE RESTRICT everywhere by default. Clinical rows are never removed
    by a cascade. Reference data uses RESTRICT so a used concept cannot vanish.

26. THE OBSERVATION MODEL (WHY IT IS BUILT THIS WAY)
--------------------------------------------------------------------------------

The single most consequential schema decision is how examination findings are
stored. Three options exist and only one survives contact with ENT.

  Option A: a wide table per exam type, one column per possible finding.
    tympanic_membrane_exam(right_perforation_quadrant_as, right_perforation_pct,
    right_retraction_sade, ...). Around 400 columns across the specialty.
    Fails because: every new finding is a migration, most columns are NULL,
    cross-exam comparison needs bespoke SQL per column, and adding the larynx
    map means starting over.

  Option B: a JSON blob per exam. Flexible and fast to build. Fails because:
    you cannot index it usefully, cohort queries ("all patients with grade 3
    polyps") become full scans, and there is no referential integrity between
    a finding and its terminology, so translations and comparisons rot.

  Option C (chosen): a typed observation table, FHIR-shaped.
    Each row is one finding: what (concept), where (body site + map region),
    which side, what value (typed), plus provenance. Multi-part findings use
    observation_component.

Why C wins here:
  - New findings are new concept rows, not migrations. A clinic can add a
    finding on a Tuesday afternoon.
  - Comparison between two visits is one query grouped by body site.
  - Cohort analytics work: value_concept_id is indexed and joinable.
  - The anatomical map, the narrative renderer, the comparison view and the
    analytics all read the same table, so they can never disagree.
  - Translation is free: the finding is a concept id, rendered in whatever
    locale the reader needs.

Where C is deliberately NOT used:
  High-volume, fixed-shape numeric data gets its own narrow table, because
  the shape genuinely never changes and query performance matters:
  audiogram_threshold, questionnaire_answer, allergy_test_result,
  acoustic_reflex. These are dense, regular and queried in bulk.

The rule: fixed and dense -> dedicated table. Sparse, extensible and
clinician-defined -> observation.

Denormalized read models (examination_snapshot, audiology_metric,
questionnaire_response.total_score) exist for speed, are always derived, and
can be rebuilt from the source rows by a maintenance job. They are never the
source of truth.

27. INDEXING, PARTITIONING AND PERFORMANCE
--------------------------------------------------------------------------------

  - Every tenant-scoped index starts with clinic_id. A query without it is a
    bug, and the repository layer prevents it.
  - Patient search: a normalized column (accent- and case-folded, Arabic
    diacritics stripped) plus a FULLTEXT index. Search both name columns and
    the alternate-script columns.
  - Timeline queries: covering index on (clinic_id, patient_id, occurred_at
    DESC) for each event-producing table, and a materialized `patient_timeline`
    read model refreshed by event handlers once volume justifies it.
  - audiogram_threshold is the highest-row-count clinical table (about 40 rows
    per audiogram). Index (audiogram_id) and (audiogram_id, ear, conduction).
  - observation is the second highest. Index as listed, and archive
    observations from encounters older than the retention window into a
    history table if volume ever demands it.
  - audit_log and access_log partitioned by month (RANGE on occurred_at).
    Keep 24 months hot, archive the rest to cold storage.
  - No SELECT *. Repositories select explicit columns for list endpoints.
  - N+1 prevention: eager loading declared in repository methods
    (selectinload for collections, joinedload for single relations), and a
    test-time query counter that fails a test exceeding its expected count.
  - Connection pool sized to the worker count; a slow-query log threshold of
    200 ms reviewed weekly.
  - Read replica later if analytics grow; selectors.py is already the only
    place that would need to point at it.


--------------------------------------------------------------------------------
28. MIGRATIONS, SEEDS AND REFERENCE DATA VERSIONING
--------------------------------------------------------------------------------

  - Alembic, one migration per change, autogenerate reviewed by hand (it
    misses index and constraint intent). Migrations are additive-first:
    add column nullable -> backfill -> enforce NOT NULL in a later migration,
    so a deploy never locks a clinic out mid-morning.
  - Every migration must be reversible or explicitly marked irreversible with
    a documented reason.
  - Data migrations live in their own migration files and are idempotent.
  - Seeds are split by purpose:
      seed_system     code systems, core concepts, value sets, permissions,
                      roles, system templates, instruments. Required in every
                      environment, versioned by reference_data_version.
      seed_demo       one demo clinic with fake patients for sales demos and
                      for local development.
      seed_test       deterministic fixtures for the test suite.
  - Reference data updates ship as versioned seed scripts, not as manual SQL.
    Applying one records a row in reference_data_version with who and when.
  - A `make anonymize` script produces a safe development dump: names, phones,
    identifiers and free text scrubbed, dates shifted by a per-patient offset,
    structure and volume preserved so performance work is realistic.

--------------------------------------------------------------------------------
29. AUTHENTICATION, AUTHORIZATION AND MULTI-TENANCY
--------------------------------------------------------------------------------

Authentication
  - Email plus password (argon2id), optional TOTP second factor.
  - Short-lived access token (15 min) in memory, refresh token in an
    HttpOnly, Secure, SameSite=Lax cookie, rotated on every use with reuse
    detection (a replayed refresh token revokes the whole session family).
  - Session lock after inactivity, short by default in shared rooms, per-clinic
    configurable. A locked screen requires the password, not a full login, so a
    doctor returning from a procedure is back in two seconds.
  - Login throttling per account and per IP; lockout with admin unlock.
  - Password reset by single-use, expiring, hashed token.

Authorization, three layers, all enforced server-side
  1. Permission: does this role have `encounter.sign`?
  2. Tenant: does this resource belong to the active clinic?
     Enforced in BaseRepository, not by remembering to add a WHERE clause.
  3. Patient scope: own patients / clinic patients / break-glass.
     Break-glass requires a typed reason, grants time-limited access, writes a
     high-visibility audit row and notifies the clinic admin.

Permission codes are grouped and explicit, for example:
  patient.read.own, patient.read.clinic, patient.write, patient.merge
  encounter.create, encounter.write, encounter.sign, encounter.amend
  prescription.create, prescription.sign
  audiology.enter, audiology.interpret
  surgery.schedule, surgery.note.write
  document.finalize, document.send
  admin.users, admin.templates, admin.terminology, admin.export

The role matrix (clinic admin, doctor, assistant, audiology technician,
read-only) is seeded data, so a clinic can create a custom role without code.

Multi-tenancy
  - Shared schema, clinic_id everywhere. A single MySQL database.
  - The active clinic comes from the authenticated session, never from a
    client-supplied header alone; the header only selects among the clinics
    the user actually belongs to.
  - A parametrized test iterates every endpoint and asserts cross-tenant reads
    return 404 (not 403, which would confirm existence).

--------------------------------------------------------------------------------
30. AUDIT, IMMUTABILITY AND SIGNING
--------------------------------------------------------------------------------

  - Writes are audited with before and after images and the changed field list.
  - Reads of clinical records are audited too (who opened which chart).
  - Signing computes a SHA-256 hash of the canonical content and stores it with
    the signer, timestamp and IP. Any later verification can prove the record
    was not altered.
  - After signing, the record is immutable at the service layer: the only
    mutation allowed is adding an addendum. The repository refuses updates to
    signed rows, and a database trigger can be added as a belt-and-braces
    guard.
  - Documents store a content snapshot of the data used to render them, so a
    report printed in 2026 can be reproduced identically in 2031 even after
    templates change.
  - Soft delete everywhere. Actual erasure only through a documented legal
    procedure that writes an erasure record.

--------------------------------------------------------------------------------
31. ERROR HANDLING CONTRACT
--------------------------------------------------------------------------------

  - One response shape for every failure: RFC 7807 problem+json with `code`,
    `context` and `requestId`.
  - Codes are namespaced and stable: `prescription.allergy_conflict`,
    `encounter.already_signed`, `audiogram.incomplete_thresholds`.
  - Validation failures return field-level errors keyed by the same path the
    frontend form uses, so they map back onto inputs automatically.
  - Unexpected exceptions return a generic code, log the full trace with the
    request id, and never leak internals to the client.
  - The frontend translates by code. Nothing displayed to a doctor is an
    untranslated server sentence.

--------------------------------------------------------------------------------
32. LOGGING, TRACING AND METRICS
--------------------------------------------------------------------------------

  - Structured JSON logs with request_id, user_id, clinic_id, route, duration.
  - Never log patient identifiers, free-text clinical content, tokens or
    passwords. A log redaction filter enforces a deny-list.
  - Correlation: request_id generated at the edge, propagated to jobs and to
    the frontend (returned in every error) so a doctor's screenshot of an error
    is enough to find the exact trace.
  - Metrics worth having from day one: request latency per route, error rate
    by code, PDF render duration, job queue depth and failure rate, questionnaire
    completion rate, login failures, slow query count.
  - Health endpoints: /health/live (process up) and /health/ready (DB, Redis,
    storage reachable).
  - Sentry or equivalent for exceptions, with PII scrubbing enabled.

--------------------------------------------------------------------------------
33. CONFIGURATION AND ENVIRONMENTS
--------------------------------------------------------------------------------

  - One settings class (pydantic-settings), all values from environment, fails
    fast at startup on a missing or invalid value. No config file read at
    runtime, no defaults that silently point at production.
  - Secrets never in the repository. .env.example lists every key with a
    comment and a safe dummy value.
  - Environments: local (docker-compose), staging (production-shaped, seeded
    with anonymized data), production.
  - Feature flags in the `feature_flag` table for gradual rollout of modules
    per clinic. A clinic that has not bought the surgery module simply does not
    see it.
  - Clinic-level clinical settings (PTA formula, asymmetry rule, polyp scale,
    tube recall interval, follow-up defaults) live in `setting`, never in code,
    and every calculation records which setting it used.

--------------------------------------------------------------------------------
34. FILE STORAGE AND MEDIA PIPELINE
--------------------------------------------------------------------------------

  Upload:  client requests a pre-signed upload URL -> uploads directly to
           object storage -> confirms to the API, which creates the attachment
           row. Large endoscopy videos never pass through the API process.
  Process: a job strips EXIF (location data in a clinical photo is a privacy
           problem), scans for malware, generates thumbnail/preview/print
           variants, extracts dimensions and duration, computes the checksum.
  Serve:   short-lived pre-signed download URLs, issued only after the same
           permission check as any other clinical read, and logged.
  Keys:    clinic/{clinicId}/patient/{patientPublicId}/{category}/{ulid}.{ext}
           Never a guessable or sequential path.
  Retention: variants regenerable, originals never auto-deleted. Lifecycle
           rules move cold media to cheaper storage after a configured period.

--------------------------------------------------------------------------------
35. API DESIGN CONVENTIONS
--------------------------------------------------------------------------------

  - Base path /api/v1. A breaking change means /api/v2, not a silent mutation.
  - Resource-oriented plural paths, public ids in URLs:
      GET    /api/v1/patients?search=...&limit=25&cursor=...
      POST   /api/v1/patients
      GET    /api/v1/patients/{patientId}
      PATCH  /api/v1/patients/{patientId}
      GET    /api/v1/patients/{patientId}/timeline
      POST   /api/v1/encounters
      PATCH  /api/v1/encounters/{encounterId}          autosave, partial
      POST   /api/v1/encounters/{encounterId}/sign     state transitions are
      POST   /api/v1/encounters/{encounterId}/addenda  sub-resources or verbs,
      POST   /api/v1/audiograms                        never PATCH status=...
      POST   /api/v1/calculators/{code}
      POST   /api/v1/documents/{documentId}/render
      GET    /api/v1/recalls?status=overdue
  - JSON is camelCase on the wire, snake_case in Python. Handled by the base
    schema, not by hand.
  - Every list response uses the same envelope with a `page` object.
  - Idempotency-Key header accepted on all POSTs that create clinical records,
    so a double-tap on a tablet cannot create two audiograms.
  - If-Match / version field on updates for optimistic concurrency.
  - Accept-Language decides the locale of any translated content in the
    response (concept displays, generated narrative).
  - OpenAPI is generated, checked into packages/contracts, and a CI job fails
    the build if the committed spec and the code disagree.

--------------------------------------------------------------------------------
36. SECURITY CHECKLIST
--------------------------------------------------------------------------------

  Transport      TLS everywhere, HSTS, no mixed content.
  Headers        CSP, X-Content-Type-Options, Referrer-Policy, frame-ancestors.
  Input          Pydantic validation on every endpoint; file type and size
                 limits enforced server-side, not just in the browser.
  Injection      Only parameterized queries through the ORM. No f-string SQL.
  XSS            React escapes by default; the only dangerouslySetInnerHTML is
                 in the document template preview, and that HTML is sanitized
                 server-side with an allow-list before storage.
  CSRF           SameSite cookies plus a CSRF token on cookie-authenticated
                 state-changing requests.
  Rate limiting  Per IP and per account on login, password reset, questionnaire
                 token endpoints and export endpoints.
  Public tokens  Questionnaire links: single-use, hashed at rest, short expiry,
                 scoped to one instrument and one patient, and they expose no
                 patient data beyond a first name.
  Encryption     TLS in transit, disk encryption at rest, application-level
                 encryption for the few high-sensitivity fields (national ID,
                 MFA secrets).
  Backups        Daily automated, encrypted, off-site, with a restore drill
                 performed and documented quarterly. An untested backup is not
                 a backup.
  Dependencies   Automated vulnerability scanning; a monthly patch window.
  Access review  Quarterly review of user roles and of break-glass events.
  Data rights    Export and erasure procedures documented and implemented, with
                 the legal retention period respected for medical records.

37. CI/CD AND QUALITY GATES
--------------------------------------------------------------------------------

Pipeline on every pull request:
  1. Lint and format        ruff + black (Python), eslint + prettier (TS)
  2. Type check             mypy strict on src/, tsc --noEmit
  3. Import boundaries      import-linter (backend), eslint boundaries (frontend)
  4. Unit tests             engines and utils, must be fast
  5. Clinical known-answer  every calculator against its published reference
  6. Integration tests      against MySQL in a service container
  7. API contract           generated OpenAPI matches the committed spec
  8. Translation check      every key present in every locale, no orphan keys
  9. Migration check        migrations apply cleanly to an empty DB and to a
                            snapshot of the previous release's schema
 10. Frontend build         Next.js production build
 11. E2E                    Playwright, the three killer workflows, in en/fr/ar
 12. Security               dependency audit, secret scanning

Coverage thresholds: 100% on engines/, 85% on services, 70% overall. The
engines number is not negotiable; that is where a wrong answer harms a patient.

Deployment: containerized, migrations run as a separate step before the new
version starts, health checks gate the rollout, one-command rollback, and a
maintenance page that never appears during clinic hours.

39. ANTI-PATTERNS: WHAT WILL KILL THIS PROJECT
--------------------------------------------------------------------------------

Ranked by how much damage they cause.

  1. Clinical math in the frontend. The moment a PTA is computed in
     TypeScript, there are two implementations and one of them is wrong. All
     math on the server, always.
  2. Findings stored as free text or as JSON blobs. You lose comparison,
     analytics and translation at once, and it cannot be fixed later without
     re-entering years of data.
  3. Hardcoded strings. Every literal in JSX or in a Python response is a
     language you cannot add later without touching every file.
  4. Storing scanned PDFs instead of numbers. An audiogram as an image is a
     dead end. Type the thresholds.
  5. God service files. `MedicalService` with 3,000 lines. Split by domain.
  6. Business logic in routers. It becomes untestable and gets duplicated the
     next time an endpoint needs the same rule.
  7. Forgetting clinic_id in a query. A cross-tenant data leak in a medical
     app is not a bug, it is an incident. Enforce it in the base repository.
  8. Mutable signed records. If a report can change silently after signing,
     the record has no legal value.
  9. Deep cross-feature imports. `import { x } from "@/features/a/components/
     internal/y"` turns the codebase into a ball of mud within a year.
 10. Wide exam tables. 400 nullable columns, a migration for every new
     finding.
 11. No pagination. A patient list query that returns 30,000 rows will be
     written by someone in a hurry. Cap it in the base repository.
 12. N+1 queries in the timeline. Twenty visits producing 400 queries makes
     the app feel broken on clinic wifi.
 13. E2E tests that click by translated button text or menu labels. They pass
     in English and fail in French, or break on every copy edit. Use
     data-testid from lib/test/test-id.ts only.
 14. Float for money or for measurements that must be exact.
 15. Cascading deletes on clinical tables.
 16. Building the AI layer before the structured data layer is solid. The AI
     is a convenience; the data model is the product.

40. BUILD ORDER FOR THE SKELETON
--------------------------------------------------------------------------------

Before any feature, build the spine. Roughly two to three weeks, and it pays
for itself by the third feature.

  Day 1-2   Monorepo, docker-compose (MySQL, Redis, MinIO), Makefile,
            settings, health endpoints, CI skeleton.
  Day 3-4   core/db: Base, mixins, session, unit of work, ULID type.
            First migration: clinic, user, role, permission.
  Day 5-6   core/security: password hashing, JWT, session, CurrentUser and
            permission dependencies. Login, refresh, logout endpoints.
  Day 7     core/errors, core/context, audit middleware, audit recorder.
  Day 8-9   core/repository: BaseRepository, filters, pagination.
            core/schemas: CamelModel, common clinical value objects.
  Day 10    core/events bus, jobs worker skeleton with one real job.
  Day 11-12 Terminology feature: concept, translations, value sets, search
            endpoint, seed script with the first anatomy and finding concepts.
            This unblocks everything clinical.
  Day 13-14 Frontend skeleton: Next.js with locale routing, middleware, shadcn
            installed, AppShell, providers, API client, query keys, test-id
            factory (lib/test/test-id.ts), generated types, login flow with
            data-testid on shell and auth, DataTable, form field library.
  Day 15    i18n end to end: catalogs for en and fr, pseudo-locale, RTL smoke
            test with a placeholder ar catalog, format helpers.
  Day 16-17 Patients feature end to end as the reference implementation:
            model, repository, service, router, schemas, tests, frontend list,
            detail, form, search. Every later feature copies its shape.
  Day 18-19 Documents: template model, HTML to PDF renderer, one real
            template printed in en, fr and ar. Prove RTL output early.
  Day 20    Attachments: pre-signed upload, variants job, viewer component.

After that, features ship in the order of the phasing plan in the feature
specification, and each one is a copy of the patients module's shape with
different clinical content.
